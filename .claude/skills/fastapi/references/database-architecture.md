# Database & architecture

## Async SQLAlchemy session lifecycle (this repo's pattern)

`backend/app/core/database.py`:
```python
engine = create_async_engine(settings.database_url, echo=settings.app_env == "development")
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)

class Base(DeclarativeBase):
    pass

async def get_db() -> AsyncSession:
    async with AsyncSessionLocal() as session:
        yield session
```
`expire_on_commit=False` matters: without it, accessing an ORM object's attributes after
`commit()` triggers a lazy-load — which fails outside the request/session scope (e.g. if
you `commit()` then serialize with a `response_model` after the session context exits).

One `get_db()`-yielded session per request, reused for every dependency/route that needs
it via sub-dependency caching (see dependencies.md). Don't create a second engine/session
elsewhere — import `get_db`/`AsyncSessionLocal` from `core/database.py`.

### Querying
```python
result = await db.execute(
    select(Project).where(Project.owner_id == current_user.id).options(selectinload(Project.milestones))
)
return list(result.scalars().all())        # many rows
return result.scalar_one_or_none()          # zero-or-one row
```
Use `.options(selectinload(...))` to eager-load relationships you'll access after the
query — accessing a lazy relationship inside `async def` code raises
`MissingGreenlet`/`DetachedInstanceError` instead of silently doing a sync lazy-load
(SQLAlchemy's async mode has no implicit lazy loading).

### Writes
```python
db.add(new_project)
await db.commit()
await db.refresh(new_project)   # repopulate server-generated fields (id, created_at, ...)
return new_project
```

## Migrations (Alembic)

This repo has Alembic configured (`backend/alembic/`). After changing a model in
`app/models/`, generate a migration rather than relying on `Base.metadata.create_all` in
production (that's test-only — see `conftest.py`'s `reset_db` fixture):
```bash
cd backend && alembic revision --autogenerate -m "add widgets table"
alembic upgrade head
```
Always review autogenerated migrations — Alembic can't detect every change correctly
(e.g. column renames show as drop+add, losing data unless you hand-edit the migration).

## Configuration (`pydantic-settings`)

`backend/app/core/config.py` defines a single `Settings(BaseSettings)`, instantiated once
as `settings`, imported everywhere as `from app.core.config import settings`:
```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", case_sensitive=False)
    app_env: str = "development"
    secret_key: str = "change-me-in-production"
    database_url: str = "sqlite+aiosqlite:///./app.db"

    @model_validator(mode="after")
    def validate_production_settings(self) -> "Settings":
        if self.app_env == "production" and len(self.secret_key) < 32:
            raise ValueError(...)
        return self
```
`pydantic-settings` reads env vars case-insensitively (`case_sensitive=False`) and falls
back to `.env` — never read `os.environ` directly elsewhere in the app; add a field to
`Settings` instead, so there's one place that documents every config value and its
default. The `model_validator(mode="after")` pattern here is the right place to enforce
prod-only invariants (e.g. "no default secret key in production") — it runs once at
import time (`settings = Settings()`), so a misconfigured prod deploy fails at startup,
not on the first request that needs the secret.

Per CLAUDE.md: don't commit `.env`; only `.env.example` is tracked. Add new settings to
`.env.example` with a placeholder value whenever you add a field to `Settings`.

## Middleware

App-wide, runs on every request/response, in the order registered (each middleware wraps
the next). This repo already has two:
```python
app.add_middleware(CORSMiddleware, ...)

@app.middleware("http")
async def log_requests(request: Request, call_next):
    started = time.perf_counter()
    response = await call_next(request)
    logger.info("%s %s %s %.2fms", request.method, request.url.path, response.status_code, ...)
    return response
```
`@app.middleware("http")` is sugar for a limited subset of ASGI middleware — fine for
logging/timing, but for anything needing the raw ASGI `scope`/`receive`/`send` (e.g.
websocket-aware middleware), write a proper `BaseHTTPMiddleware` subclass or ASGI
middleware class and add it via `app.add_middleware(...)` instead.

Middleware registered via `add_middleware()` wraps handler-based (`@app.middleware`)
middleware — `add_middleware` calls form the *outer* layers, decorator-based middleware
the *inner* layers, regardless of source order between the two styles. Within the same
style, order of registration = outer-to-inner.

## Lifespan (startup/shutdown)

Use the `lifespan` async context manager, not the deprecated `@app.on_event("startup")`:
```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup: e.g. warm a cache, verify DB connectivity
    yield
    # shutdown: e.g. close connection pools, flush logs

app = FastAPI(lifespan=lifespan)
```
Code before `yield` runs once before the app accepts requests; code after runs once after
the app stops accepting new requests. Good place for expensive one-time setup that
route-level dependencies would otherwise redo per-request (e.g. loading an ML model,
opening a long-lived external connection pool that isn't the per-request DB session).

## Sub-applications & mounting

`app.mount("/admin", admin_app)` mounts an entirely separate `FastAPI` instance (own
OpenAPI schema, own middleware stack) at a path prefix — different from `APIRouter`
(same app, shared schema/middleware). Reach for this only when you genuinely need
isolation (e.g. a legacy app being incrementally replaced); for normal feature
separation within this repo, use `APIRouter` as already established in `app/api/`.

## Behind a reverse proxy

If this app is ever deployed behind Nginx/Traefik with a path prefix (e.g.
`/api` stripped before reaching FastAPI), set `root_path` on the `FastAPI()` constructor
or the `--root-path` CLI flag so generated URLs (in OpenAPI, redirects) include the
prefix the proxy expects. Getting this wrong manifests as `/docs` loading but its
"Try it out" requests 404ing, because the OpenAPI spec's server URL is missing the prefix.
